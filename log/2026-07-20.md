## 原则问题（今日敲定，有承重意义）

**核心原则：「精确写、模糊读」**

去重不是一件事，是性质不同的两件事，必须分层：

| | 精确匹配 | 模糊匹配 |
|---|---|---|
| 判据 | DOI / arXiv base id / resource_id 等值 | 标题近似、预印本 vs 正式发表是否同一篇 |
| 谁来做 | 确定性 Python（resolver + dedup） | LLM 判断 |
| 守什么 | INV1（一篇论文最多一个 Zotero 条目），有 eval 守护 | 只出候选，不下结论 |
| 出错兜底 | 有测试钉死 | NG3：写路径模糊命中 → conflict → 人工，绝不自动合并 |

**为什么不接受「单张外部表 + 纯 LLM 去重」（用户原始设想，讨论后否决）：**

1. 会让 INV1 变成非确定性 —— 无法用回归测试守护（违反 G7）。
2. 会违反 G8：底层能力未来要能脱离 Claude、用确定性 CLI 复用；去重只活在 LLM 里，CLI 单跑就不去重了。
3. 拿 Obsidian 索引（INV4 明确是「可重建的派生索引」）当权威判据 = 把派生表提拔成权威账本，
   索引过期 / 重建就会漏判导致重复进 Zotero。

**澄清的一个误解：「表放插件外」≠「必须用 Obsidian 索引」。**
`state.db` 本就在配置路径、不进 git 仓库，已满足「插件外」；且 INV7 说状态库正是存映射的地方，
`resource_id → zotero_key` 这种去重映射本就是它的职责。所以登记表有个现成且合规的家。

**结论**：精确层用确定性代码守硬线，模糊层交给 LLM 做判断力活儿，两不相扰。
如果哪天真要走「纯 LLM 去重」，那不是实现选择，是改 GOALS（重定义 INV1 守护方式、放松 G8），需另行拍板。
