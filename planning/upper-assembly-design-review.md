## 已明确的用户要求

### 项目

- 被管理的科研项目以内部 `PROJECT.md` 详尽介绍项目；对外展示和发布仍使用 `README.md`。
- `PROJECT.md` 包含最新情况、代码入口、相关论文与其他资料、实验入口及代码模块关系图。
- 项目主要在 VS Code 中阅读，链接应能定位实际代码、配置、实验及资料，而不是跳过多层中间页。
- 包含项目计划。详细计划较长时可单独用 `SCHEDULE.md`，但同一计划不维护两套独立真源。
- 用户评价项目管理草图“格式还算满意”；这不是实际项目链接、内容或安装态验收通过。
- “不发布”不自动意味着从内部 Git 排除，也不授权删除现有 README 或其他说明。
- 此处的 `PROJECT.md` 指被管理科研项目的内部入口，不恢复本插件已归档的旧架构文档。

### 知识与文献

- 以已有论文单元为基础组织领域，不重新分析所有论文，也不复制出另一套论文真源。
- 需要清晰、美观的论文整理列表，以及能够解释技术取舍、原因和效果的 literature tree。
- 文献演进图改为纵向发展，主线向下，主要支线并行；局部进展与主干区分。
- 框体更小、更紧凑，但不靠缩小正文、裁切或删除内容获得紧凑效果。
- 保留单篇论文既有完整五分支、可编辑 Canvas、对齐/无交叉、证据反链、原文位置、
  正文折叠摘录及已确认的原图呈现要求。本轮上层视图不替代单篇解析树。

四类 novelty 是贡献性质，不是质量评分：

| 类别 | 用户定义 | 演进图位置 |
|---|---|---|
| 1 | milestone task 的 seminal work | 可进入主线或主要支线 |
| 2 | novel pipeline / representation 的 seminal work | 可进入主线或主要支线 |
| 3 | novel module 的 seminal work | 所属路线的局部进展，不因模块首创自动升入主干 |
| 4 | 加入 module 改进已有 pipeline 的工作 | 所属路线的局部进展 |

只有 1/2 类贡献具备主干资格，不意味着所有 1/2 类都必须占据主干。
同篇可有多项贡献，按贡献分别说明并复用同一论文身份；3/4 类可能重叠，不强制互斥。
开创性证据不足时标待定，不把无法分类的论文自动塞进第 4 类。
“在所考察文献中最早”不能冒称全球首创。分类、科学支持与视觉评鉴分别判断。

## 呈现内容建议（尚非正式模板）

### PROJECT.md

建议依次展示：项目目标与最新情况、代码模块/数据流及源码配置链接、研究资料、
实验与结果、里程碑和近期计划、关键决定与剩余问题。
当前情况应有核验时间与依据；实验数值来自记录，不能为填满门面发明结果。
PROJECT 复用现有项目身份和资料清单，不建立新的全局状态服务或 Hub 前置条件。

### Literature tree

主干和主要支线只展示具备资格且有证据的 1/2 类贡献；3/4 类按所属路线局部展开。
每项演进说明要能看到：相对谁、改变了什么、为何作此选择、证据支持的收益与代价、
比较成立的条件及原文确切入口。作者动机、实验事实和分析者推断分别标明。
指标不同设置、任务不同或未直接比较时明确限制，不强排优劣。

正式采用何种可编辑载体、图片密度、论文列表列项及布局细节仍需确认。
会话里的可点击草图不是新增前端产品，也不代表 Obsidian 内交互已经实现。
论文关键图在草图中只是明确标记的占位，没有伪造科学图像或真实论文结论。

### 实验比较

沿用 Run/Attempt/Target/Artifact 身份与冻结输入，不另建实验真源。
比较需展示所选 Run、数据及切分、评价协议、配置差异、指标单位和对应成果入口。
不可比项保留原因；重试不算独立重复实验，提升均值或置信结论需要对应统计依据。
具体表格和图形尚未定稿，不在本轮执行新实验。
